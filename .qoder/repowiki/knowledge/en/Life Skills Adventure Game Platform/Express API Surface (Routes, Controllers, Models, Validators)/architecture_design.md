The module is organized as a classic layered Express/Sequelize application split across four sibling directories:
- `routes/`: One Express Router per domain (`auth`, `game`, `profile`, `progress`, `scenario`, `score`, `skill`, `resource`, `lifeguide`, `admin`, `analytics`). Each route file composes middleware in a fixed order — rate limiting (`authLimiter`/`otpLimiter`), authentication (`authMiddleware`), and input validation (`validate(schema)`) — before dispatching to a controller method.
- `controllers/`: Thin handlers that parse `req.body`, call domain services (e.g. `otp-service`), interact with Sequelize models via `../models/index.js`, and return JSON responses. All async handlers are wrapped with `asyncHandler` from `utils/async-handler` so errors propagate uniformly.
- `models/`: Sequelize model definitions using `DataTypes`. Relationships (hasOne, hasMany, belongsTo, belongsToMany through `ScenarioResource`) are declared centrally in `index.js`, which also re-exports all models for use in controllers. Default scopes hide sensitive fields like `passwordHash` and `tokenVersion` unless explicitly requested via a `withAuth` scope.
- `validators/`: Joi schemas grouped by feature (`auth-schemas.js`, `game-schemas.js`) and imported into routes so validation rules live next to the endpoints they guard.

Dependency direction is strictly one-way: routes → controllers → models/services; validators are consumed only by routes. Cross-cutting concerns (auth, rate limiting, validation, error handling via `AppError`) are externalized into `middleware/` and `utils/`, keeping this surface layer declarative.
